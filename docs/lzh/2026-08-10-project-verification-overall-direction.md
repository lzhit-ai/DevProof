# 项目整体核验与后续开发方向

> 状态：已确认的产品与架构方向。本文用于约束后续改造；其中标为“待实现”的能力不代表当前代码已经具备。

## 1. 产品边界

本产品面向开发者及研发团队，目标是建立可追溯的研发交付事实链，而不是：

- 让模型无边界阅读整个仓库并给出“全项目代码审查”结论；
- 以 Git 提交数量或提交说明推断项目完成度；
- 以通用 Agent 编排替代项目管理、代码审查或安全平台；
- 自动执行仓库代码、构建、测试、修复、提交或发布。

产品应提供三条独立业务线，共用同一套项目、来源、快照、证据和正式记录：

| 业务线 | 解决的问题 | 主要输出 |
| --- | --- | --- |
| 交付核验 | 某个研发交付是否被目标和实际证据支持 | 交付核验记录 |
| 项目态势与研发总结 | 项目范围、进度、风险和数据缺口如何 | 日报、周报、迭代或项目总结 |
| 安全与质量治理 | 指定仓库版本有哪些已发现风险、覆盖范围如何 | 安全基线与风险记录 |

三条业务线可以引用彼此的正式记录，但不能互相改写结论。

## 2. 名词与职责

### 2.1 研发事项 / 交付项

“支付重试改造”“订单取消能力”“迭代目标”是项目中的结构化对象，不是 Agent，也不是一次 Git Diff 审查。

交付项由外部事实来源同步或提取：Issue、Jira、GitHub/GitLab Milestone、需求文档、设计文档等。本系统保存其来源、版本、同步时间和关联关系，不以在本系统手工编写内容作为主要事实来源。

### 2.2 交付核验

一次交付核验围绕一个已确定的交付项发起，并绑定一个明确的 Git Diff/PR 范围。它回答：这次变更是否支持该交付项的验收目标。

### 2.3 项目态势与研发总结

项目态势是多个事项、计划、交付记录、风险和实时状态的汇总判断。它不是一次代码核验运行，也不能把未核验事项写成已完成。

### 2.4 安全基线

安全基线是针对指定仓库版本和指定扫描范围的风险治理过程。它不是普通 Git Diff 核验，也不是“模型通读完整仓库后宣布项目安全”。

## 3. 固定双核的边界

双核是交付核验的不可替代主干，而不是每一种外围能力都必须运行的通用 Agent。

1. **目标 / 验收核验核心**
   - 输入：需求、设计、验收条件等已冻结的权威资料。
   - 输出：可追溯的 `Claim`，即“本次交付应满足什么”。

2. **实际交付证据核验核心**
   - 输入：已冻结的 Git Diff/PR、受影响代码上下文、已导入且绑定提交 SHA 的 CI/测试结果。
   - 输出：代码与交付证据，即“本次实际改了什么”。

3. **证据裁决规则**
   - 属于平台确定性规则，而不是第三个可随意替换的核心 Agent。
   - 对齐 `Claim` 与证据，结果只能是：已确认、部分支持、存在冲突、证据不足、推断或待确认。

PR、分支或 Issue 的关联只用于确定“本次 Diff 对应哪个交付项”，不能证明功能已经实现。真正的核验必须读取具体 Diff、改动文件、必要的受影响代码上下文和测试/CI 证据。

## 4. Git Diff 的正确位置

Git Diff 是 **交付核验配置** 的锁定默认输入，不是所有系统功能的全局前置条件。

| 运行配置 | 是否运行双核 | Git Diff 是否必需 | 结论边界 |
| --- | --- | --- | --- |
| `DELIVERY_VERIFICATION` 交付核验 | 是 | 是 | 指定交付项在指定变更范围内是否被证据支持 |
| `PROJECT_STATUS_SUMMARY` 项目态势总结 | 否，读取双核历史记录 | 否 | 截至某一时间点的项目态势与数据缺口 |
| `SECURITY_BASELINE` 安全基线 | 否，使用安全专用能力 | 不以 Diff 为主 | 指定 SHA、规则和覆盖范围内的风险 |
| `QUALITY_TREND` 质量趋势 | 否 | 否 | CI、测试、缺陷、风险的趋势 |

用户应选择业务意图，例如“核验本次交付”“生成本周研发总结”“执行安全基线”，而不是选择抽象的“审 Diff”或“审全仓代码”技术模式。

## 5. 多来源事实与冲突规则

文档和 Git 平台都应接入，但各自只解释自己负责的事实。

| 事实 | 首选来源 | 不能替代的事实 |
| --- | --- | --- |
| 项目目标、能力范围、验收条件 | 需求/设计文档，或 Issue 的验收字段 | 实际代码是否实现 |
| 事项、负责人、计划状态、里程碑 | Issue/Jira/Git 平台 Milestone | 是否已经核验通过 |
| 实际变更 | PR、Git Diff、提交、目标 SHA | 业务目标本身 |
| 构建、测试、安全扫描 | CI 与受控扫描工具的结果 | 需求是否合理或项目是否完成 |
| 正式核验状态 | 本系统已人工确认并固化的记录 | 外部平台的计划状态 |

事项状态必须保留两个独立维度：

- **外部计划状态**：未开始、进行中、已完成、已取消；
- **本系统核验状态**：未评估、部分支持、已确认、存在冲突、证据不足。

当外部事项显示“已完成”而不存在正式交付记录时，项目态势只能表达为“外部状态已完成，尚未核验”。

## 6. 事项与代码变更的关联

提交说明并不可靠，不能作为完成度判断的必要条件。关联按可靠性分层：

| 关联方式 | 处理方式 |
| --- | --- |
| PR 已明确关联 Issue/任务 | 可作为正式关联 |
| Git 平台同步到的分支、PR、事项关系 | 可作为正式关联 |
| 用户确认 PR 对应某一交付项 | 可作为正式关联 |
| Agent 根据模块、路径、文本推断 | 仅作为待确认候选 |
| 无任何关联 | 标记为未归属开发活动 |

未归属开发活动可以进入项目态势的“需要归类”列表，但不得计入任一交付项的已完成或已核验进度。

## 7. 项目整体判断的形成方式

项目整体判断不是单一分数，而是带版本、时间和覆盖边界的态势快照。

项目态势 Agent 读取：项目计划版本、事项镜像、已确认关联、交付核验记录、实时运行状态、未归属开发活动、CI/测试结果与安全风险记录。

输出至少分为以下维度：

| 维度 | 可确认的表达 |
| --- | --- |
| 范围推进 | 已核验完成、进行中、未开始、无证据、已取消 |
| 交付质量 | 已确认、部分支持、存在冲突、证据不足 |
| 研发活动 | 已关联交付、未归属开发活动、长期无变更 |
| 安全与质量 | 指定范围内的风险、构建/测试状态、覆盖缺口 |
| 数据可信度 | 来源时间、版本、缺失资料、未覆盖范围 |

项目完成率只有在存在已冻结计划基线和事项总量时才可计算；没有分母、未关联或未核验的变更不能被包装成进度。

## 8. 安全基线的范围

安全基线可以覆盖整个仓库版本，但流程应为“自动扫描全仓 + Agent 定向解释”，而不是“LLM 无边界读完整仓库”。

1. 冻结目标分支或目标 SHA。
2. 导入或运行绑定该 SHA 的依赖、密钥、配置、静态规则等扫描结果。
3. 记录扫描器、规则版本、扫描路径、排除项、失败项和覆盖率。
4. 安全 Agent 对结果去重、归类，并只在风险点读取必要代码上下文。
5. 形成安全基线记录与风险清单。

正式结论必须限定为“在指定 SHA 与覆盖范围内发现的风险”，不能写成“整个项目绝对安全”。首期也不承诺替代完整 SAST/DAST 平台。

## 9. 外围 Agent 的权限模型

外围 Agent 可由用户组合 Prompt、参数和受控只读工具，但必须声明输入 Schema、输出 Schema、工具授权和适用运行配置。

它们只能产生：证据候选、风险发现、关联建议、总结草稿或结构化建议。

它们不能：

- 修改 Git、执行仓库代码、构建、测试、修复或提交；
- 直接创建 `CONFIRMED` 核验结论；
- 修改已冻结输入快照、历史证据或正式记录；
- 审批、固化正式记录；
- 将临时 HTTP 查询结果直接当作正式证据。

外部工具返回若要用于正式记录，必须先作为可追溯来源导入，并在新的输入快照中冻结。

## 10. 正式记录

界面中的“发布”应统一表述为 **固化正式记录**，避免被理解为代码部署或面向最终用户发布功能。

正式记录至少分为：

- 交付核验记录：支持“该交付项已在指定范围内核验”的判断；
- 安全基线记录：记录特定版本的风险和覆盖边界；
- 项目/迭代总结记录：记录某个时间点的态势，不替代实时状态。

正式记录需绑定输入快照、运行配置、报告内容哈希、审批人、时间和记录编号。个人模式允许“个人确认”，但必须明确标识，不能伪装成独立团队审批。

## 11. 目标信息架构

项目空间建议包含：

- 项目概览：态势、风险、近期活动；
- 研发事项 / 交付项：外部同步和关联状态；
- 交付核验：围绕事项、PR、Git Diff 的双核运行；
- 安全与质量：安全基线、CI、测试、依赖风险；
- Agent 功能块：受控 Prompt、工具和模板；
- 正式记录：交付、安全、总结三类记录；
- Notebook：一次事项或运行的下钻详情，不作为独立项目导航中心。

用户启动交付核验的正确操作是：选择已同步事项 → 选择或确认 PR/Git Diff → 加载目标资料 → 启动双核 → 查看证据和 Coverage → 人工确认后固化记录。

## 12. 当前实现与目标架构的差距

以下是后续需要改造但尚未实现的部分：

1. 当前 Git Snapshot 仍被全局要求；应改为只在 `DELIVERY_VERIFICATION` 中强制。
2. 当前没有外部 Issue、Milestone、PR 与文档来源的同步镜像及关联模型。
3. 当前的核验任务语义仍偏向单一交付核验，尚未拆出研发事项/交付项与项目态势快照。
4. 当前项目总结、日报、周报和安全基线尚未形成独立运行配置与正式记录类型。
5. 当前 Notebook 使用 UUID 读取真实运行；后续应由真实项目、事项和运行列表承接，UUID 不应暴露为日常用户操作。
6. 当前受控 HTTP 工具结果仍需进一步收紧：临时运行结果不得绕过导入与冻结流程成为正式引用。

已存在的双核、Git Diff 核验、冻结编排、只读工具边界、报告草稿和人工审批链应保留并成为后续扩展的基础。

## 13. 建议实施顺序

1. 引入运行配置类型与快照规则，完成 Git Diff 全局强制约束的收敛。
2. 建立外部来源、来源版本、研发事项/交付项和关联关系。
3. 将现有核验任务绑定到交付项，双核只服务交付核验。
4. 建立项目态势投影和日报/周报/迭代总结草稿。
5. 建立安全与质量基线输入、覆盖表达和风险记录。
6. 调整工作台导航与详情页，使用户按交付、态势、安全和记录使用产品。
7. 为每个独立能力进行中文 Git 提交，并同步更新 `docs/lzh/feature-doc-viewer.md`；由项目使用者自行推送远端。

## 14. 核心原则

- Git Diff 证明“实际发生的变更”，不单独证明“需求已完成”。
- Issue/任务关联证明“变更属于哪个事项”，不单独证明“代码已实现”。
- 正式交付记录证明“在指定输入范围内已完成核验”，不代表项目整体完成。
- 项目总结基于计划、事项和记录汇总，不依赖提交数量或提交说明。
- 全仓安全治理依赖可记录覆盖边界的扫描与定向分析，不依赖无边界读码。
- 任何 Agent 都不能越过快照、证据、审批和正式记录边界。
