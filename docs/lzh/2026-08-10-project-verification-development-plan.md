# 项目整体核验开发方案

> 依据：《项目整体核验与后续开发方向》
>
> 状态：开发规划已确认，尚未开始本轮业务代码改造。本文中的“已完成”来自源码与近期提交审计，不等同于真实环境联调已经完成。

## 1. 实施目标

将当前“单次交付核验”能力扩展为三条边界清晰、共享事实层的业务线：

1. **交付核验**：双核以需求/验收资料和 Git Diff/PR 为输入，判断某个交付项是否被证据支持。
2. **项目态势与研发总结**：基于计划、外部事项、已关联交付记录和实时状态形成摘要，不把提交活动误写成完成。
3. **安全与质量治理**：基于指定 SHA 的扫描、CI、依赖和配置证据形成风险基线，不让模型无边界阅读全仓代码。

本轮改造的首要原则是：**保留并收紧既有交付核验链；新增项目态势和安全基线，不把它们伪装成 Git Diff 代码审查。**

### 2.4 明确不做或后置

- 无边界的“AI 审查整个项目源码”；
- 以 Git 提交数量、提交说明或 Agent 推断自动确认项目完成；
- 完整 SAST/DAST 平台、任意代码执行、自动构建/测试/修复/提交；
- 由模型自主选择外部 URL、执行写操作或直接改变正式结论；
- 将项目管理系统完整复制到本产品中；
- 多仓库、复杂 Webhook、SSO、计费等重型平台能力。

## 3. 目标领域模型

### 3.1 统一事实层

新增或扩展以下对象，所有外部内容都要保存来源、版本、抓取时间、内容哈希和同步状态：

| 对象 | 职责 |
| --- | --- |
| `ExternalConnection` | 一个项目接入的 Git 平台或文档来源配置；只保存凭据引用，不保存明文凭据 |
| `ExternalResource` / `ExternalResourceRevision` | 外部 Issue、Milestone、PR、文档等不可变版本镜像 |
| `SourceSyncRun` | 同步时间、覆盖范围、成功/失败、游标和错误摘要 |
| `DeliveryItem` | 从外部事项或文档提取出的研发事项/交付项；不以本系统手工内容为主要事实来源 |
| `DeliveryItemSourceLink` | 交付项与 Issue、文档段落、里程碑等目标来源的关系 |
| `DeliveryChangeLink` | 交付项与 PR、分支、Git Snapshot 的已确认或候选关系 |
| `ProjectHealthSnapshot` | 特定时间点的项目态势输入、覆盖范围和汇总结果 |

既有 `SourceRevision`、`GitSnapshot`、`InputSnapshot`、`AnalysisRun`、`ReportVersion` 和 `PublishedRecord` 保留，按新运行配置被复用或扩展。

### 3.2 状态规则

`DeliveryItem` 必须分离两种状态：

- `planningStatus`：来自外部事项的未开始、进行中、已完成、已取消；
- `verificationStatus`：来自本系统的未评估、部分支持、已确认、存在冲突、证据不足。

外部状态与核验状态互不覆盖。外部事项显示“已完成”但没有正式交付记录时，态势中显示“已声明完成，尚未核验”。

### 3.3 关联规则

关联按可信度处理：

1. 外部平台已存在的 Issue—PR—分支关系：正式关联；
2. 用户确认的 PR—交付项关系：正式关联；
3. Agent 基于模块、路径或文本提出的关系：候选关联，等待确认；
4. 无关联的提交/Diff：未归属开发活动，不计入完成度。

## 4. 运行配置与快照规则

引入 `AssessmentProfile`，作为模板、快照、运行、报告和正式记录的共同分类字段。

| Profile | 必需输入 | Workflow | 正式结论 |
| --- | --- | --- | --- |
| `DELIVERY_VERIFICATION` | 目标资料 + 冻结 Git Diff；可选 SHA 绑定 CI | 现有双核交付图 | 指定交付项在本次变更内的核验结果 |
| `PROJECT_STATUS_SUMMARY` | 计划/事项版本、正式记录、实时状态、风险和截止时间 | 项目态势图 | 项目态势、风险、数据缺口，不宣布未核验事项完成 |
| `SECURITY_BASELINE` | 目标 SHA、扫描结果、扫描器/规则版本、覆盖清单 | 安全基线图 | 指定范围内的风险与覆盖边界 |
| `QUALITY_TREND` | 时间范围内 CI/测试/风险记录 | 质量趋势图 | 趋势与缺失数据，不形成交付确认 |

实现约束：

- 现有全部历史快照、运行、报告和已固化记录在迁移中标记为 `DELIVERY_VERIFICATION`；不得重新计算历史哈希或篡改历史内容。
- `InputSnapshotGit` 继续在交付核验中强制存在；其他 Profile 不创建或不要求该绑定。
- `AnalysisRun` 的幂等键必须包含 Profile 和相应输入快照哈希。
- 模板验证由“Profile 的必需能力”决定：仅交付 Profile 需要双核和 Git Diff。

## 5. 功能切片与实施顺序

### 切片 1：运行范围模型与兼容迁移

**目标**：让 Git Diff 从全局约束收敛为交付核验约束，同时完全保留现有交付链。

- 新增 `AssessmentProfile` 及迁移默认值；
- 为模板、快照、运行、报告/记录增加 Profile 或记录类型；
- 重构快照与分析启动校验；
- Worker 增加 workflow dispatcher，首期仍只实际执行交付核验图；
- 交付模板继续锁定双核与 Git Diff。

**验收**：旧交付历史仍可查询；新交付核验仍要求 Git Diff；非交付 Profile 在其专用 workflow 完成前不对用户开放启动入口，避免产生无法执行的运行。

**建议提交**：`功能：区分交付核验运行范围`

### 切片 2：外部来源与研发事项镜像

**目标**：让事项和计划拥有可追溯的外部事实来源，而不是在本系统手工维护。

- 建立来源连接、资源版本、同步记录和凭据引用模型；
- 建立连接适配器接口；首个具体适配器应选择项目实际使用的 Git 平台，文档来源复用既有资料版本机制；
- 将同步到的 Issue/Milestone 与文档目标映射为 `DeliveryItem`；
- 展示同步状态、来源时间、资源版本和冲突/失败。

**验收**：一个交付项可追溯到至少一个外部事项或文档版本；同步失败不会覆盖历史镜像；用户不能把本系统本地文本伪装为外部事实。

**建议提交**：`功能：同步研发事项与外部来源`

### 切片 3：事项、PR 与 Git 范围关联

**目标**：将“目标是什么”和“本次代码改了什么”可靠地连接起来。

- 新增 `DeliveryItemSourceLink`、`DeliveryChangeLink` 与候选关联状态；
- 导入平台已有 PR/Issue 关系；
- 提供用户确认关联的命令和审计事件；
- Agent 只可写入候选关系，不能自动升级为正式关系；
- 为既有 `VerificationTask` 增加可空 `delivery_item_id`，历史任务显示为“历史未关联”，不强行补写。

**验收**：只有已确认关联的 PR/Diff 能被纳入事项进度；无关联变更进入“待归属开发活动”；交付核验仍逐段读取具体代码 Diff，而不是只检查 PR 标签。

**建议提交**：`功能：关联研发事项与交付变更`

### 切片 4：项目态势与研发总结

**目标**：从事实层生成项目级判断，不用 Diff 或提交数量冒充整体进度。

- 新增项目态势快照、期间/里程碑筛选和数据新鲜度；
- 汇总计划范围、事项状态、关联交付记录、未归属活动、风险与实时运行状态；
- 生成日报/周报/迭代总结草稿；
- 支持固化“项目/迭代总结记录”，但不改变任何交付结论。

**验收**：已核验完成、外部已完成但未核验、进行中、无证据、未归属活动被清楚区分；没有计划分母时不显示虚假完成率。

**建议提交**：`功能：生成项目态势与研发总结`

### 切片 5：安全与质量基线

**目标**：提供项目范围的风险治理，但不将它伪装成全仓 AI 读码或完整 SAST。

- 建立 SHA 绑定的扫描输入、扫描器/规则版本、路径覆盖与排除项；
- 导入受控安全、依赖、密钥、配置、CI 等结果；
- 实现安全基线图，Agent 仅对结果归并、解释，并在风险点定向读取上下文；
- 固化安全基线记录和风险状态。

**验收**：每条风险能追溯到 SHA、扫描器和规则版本；报告明确覆盖和未覆盖范围；不输出“项目绝对安全”或“发布通过”。

**建议提交**：`功能：建立项目安全与质量基线`

### 切片 6：工作台真实数据与导航重构

**目标**：让用户按业务意图操作，而不是粘贴 UUID 或面对技术模板。

- 增加项目列表和真实项目切换；
- 将“任务中心”调整为“研发事项 / 交付项”，下钻到关联 PR、交付核验和 Notebook；
- 增加项目概览、项目态势、安全与质量、正式记录页面；
- 移除工作台、任务、审批与交付历史的 fixtures；
- Agent 功能块增加 Profile 标识与适用范围说明；UUID 只保留在内部路由/API 中。

**验收**：用户从项目概览可进入事项、确认关联、发起交付核验、查看正式记录；不需要复制项目 UUID；现有浅色企业工作台风格保持不变。

**建议提交**：`功能：重构项目核验工作台导航`

### 切片 7：受控工具与历史记录收口

**目标**：消除临时工具输出进入正式引用链的风险，并完善历史可读性。

- 将运行时工具结果标记为临时运行产物；
- 新增显式“导入为来源并冻结”的流程；
- Citation Resolver 只接受当前快照中已冻结的来源证据；
- 补充旧交付记录、新类型记录和个人确认标识的详情展示。

**验收**：HTTP/外部工具临时返回不能被直接引用到正式记录；历史交付记录仍可完整回放。

**建议提交**：`功能：收紧工具证据与正式记录边界`

## 6. 依赖关系

- 切片 1 是全部后续能力的前置条件。
- 切片 2 是切片 3 和切片 4 的前置条件。
- 切片 3 是交付核验真正支撑项目进度的前置条件。
- 切片 4 与切片 5 可以在切片 1 完成后分别推进，但都依赖真实项目工作台展示。
- 切片 6 在各后端能力拥有稳定查询接口后实施，避免再次以 fixtures 过渡。
- 切片 7 可在切片 1 后提前处理，也必须在任何新的外部工具/扫描器接入前完成。

## 7. 数据迁移与兼容策略

1. 只追加迁移，不重写已发布快照、报告、审批或正式记录。
2. 所有现有数据默认归类为 `DELIVERY_VERIFICATION`。
3. `VerificationTask.delivery_item_id` 初期允许为空；历史任务不自动猜测归属。
4. 新增连接、事项、关联和项目态势对象时，以新的表和外键承接，避免改变现有证据主键语义。
5. 迁移完成后再切换服务校验；先保证旧交付运行继续有效，再开放新 Profile。

## 8. 文档、提交与验证规则

- 每个功能切片完成后使用一个中文 Git 提交，不推送远端；推送由项目使用者执行。
- 每次提交同步更新 `docs/lzh/feature-doc-viewer.md`，记录已完成、当前在做、尚未实现和本次提交。
- 任何正式结论变化必须有对应的数据迁移、API 契约、快照规则和界面状态说明。
- 当前用户未授权运行测试；实施阶段默认不运行测试套件。需要验证时，以用户后续授权为准，并优先进行静态检查、后端编译检查和前端构建检查。

## 9. 本轮开始实施前的确认点

开发顺序已经明确。真正开始切片 2 时，只需确认第一个外部 Git 平台适配器对应项目实际使用的平台；该选择不会改变本文件规定的通用来源、镜像和关联模型。
